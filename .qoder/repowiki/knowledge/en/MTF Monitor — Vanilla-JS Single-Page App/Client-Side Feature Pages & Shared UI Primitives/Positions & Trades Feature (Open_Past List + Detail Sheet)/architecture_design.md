Three-layer split inside the module:
- Data layer: `PositionRepository.js` and `TransactionRepository.js` extend `global.BaseRepository` to read/write the flat `positions/{uid}/items` Firestore sub-collection via batched writes keyed by `${ownerUid}_${item.id}`; both cache items in-memory keyed by document id.
- Service layer: `positions-service.js` owns the persistence contract — it reads/writes `mtf_tracker_data`, `mtf_transactions`, and `mtf_watchlist` from `localStorage`, applies legacy migrations (decoupling transactions/watchlist out of the main payload), strips smoke trades, optionally pushes to cloud through `global.MTFDb.bumpLocalVersionAndPush` / `applyRemoteVersion` hooks, and exposes `getTransactions`, `getOpenTransactions`, `getClosedTransactions`, `addTransaction`, `updateTransaction`, `deleteTransaction`, `getPositionsFeed`, `updatePositionsItem`, `deletePositionsItem` via `global.MTFDbRegister`.
- Presentation layer: `trades-page.js` is the render organism for the open/past/all list view, handling per-mode pagination (`tradeListPages.trade|past|all`), filter/search/sort chains, and a shared `loadMoreTrades(variant)` global handler that appends DOM batches without re-rendering. `past-page.js` is a thin wrapper delegating to `renderCurrentView` plus its own PNL options.
- Detail sheet: `trade-detail-page.js` owns a full-height bottom-sheet pane (`createAppPane('#tradeDetailSheet')`) rendering price inputs, cost cards, timeline, notes, and action buttons, all composed via `MetricsGrid.grid(renderMetricsCell(...))` cells so the design system stays consistent across list and detail.

Dependency direction is one-way: pages → service/repository; the service depends only on `global.MTFComponents`, `global.MTFAppHelpers`, and `global.MTFDb` (registered elsewhere). Each file self-registers its public API through `global.MTFRegister({ ... })` and is wrapped in an IIFE exposing globals as a fallback.
