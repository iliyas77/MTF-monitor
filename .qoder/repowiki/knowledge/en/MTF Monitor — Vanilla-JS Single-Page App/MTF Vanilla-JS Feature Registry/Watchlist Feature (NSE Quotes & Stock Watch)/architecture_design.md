Three-file leaf module split by concern:
- `watchlist-page.js` — pure presentation layer. It reads data from the global `MTFAppHelpers.marketPages` contract (`getMarketQuotes`, `getMarketError`, `syncMarketSubTabUI`) and from `global.MTFComponents.renderPageEmptyCard`, then builds HTML strings (price/change/abs-change formatters, sparkline SVG, carousel cards) and registers its renderers through `global.MTFRegister({ renderMarketQuoteRow, formatChangePct, formatChangeAbs, renderMarketPage })`. It never touches persistence.
- `watchlist-service.js` — thin orchestration shim on top of the same `MTFAppHelpers` / `MTFDb` globals. It re-exports `getWatchlistQuotes`, `getWatchlistFeed`, `updateWatchlistItem`, `deleteWatchlistItem` under `global.MTFAppHelpers.watchlistPages` and also registers itself via `MTFRegister({ watchlistService: ... })` so other features can call it.
- `WatchlistRepository.js` — data-access class extending `global.BaseRepository` (injected at runtime). It owns the flat `watchlists/{uid}/items` Firestore sub-collection, caches items in an internal Map keyed by symbol, and provides `fetch/add/remove/save` with optimistic cache updates, batch deletes, and `serverTimestamp()` writes. A singleton instance is exposed as `global.watchlistRepo`.

Dependency direction is one-way: page → service → repository → Firestore; the repository depends only on `BaseRepository`, `firebase.firestore`, and `global.MTFLogger`. Cross-feature communication happens exclusively through the global registry (`MTFRegister` + `MTFAppHelpers`), not through imports.
